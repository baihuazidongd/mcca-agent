# pi-dsh-bridge

Run DeepSeek Harness (dsh) and pi side by side on one plugin library, one MCP
registry and one skills directory — without modifying either runtime.

## What it is

Two agent runtimes are installed from npm: DeepSeek Harness (`@deepseek-ai/dsh`)
and pi (`@earendil-works/pi-coding-agent`). Each has its own extension
mechanism, its own tool schema and its own way of discovering plugins, so a tool
written for one does not work in the other.

This project puts a small neutral contract between them. A plugin author writes
against one API — `packages/plugin-sdk` — and two adapters translate that API
into each runtime:

- `packages/pi-adapter` registers the plugin as a pi extension.
- `packages/dsh-adapter` registers it as a dsh Cordis bundle.

Neither runtime is patched or forked. dsh is mounted through its own profile
patch layer plus a generated `--patch` overlay, so upgrading dsh does not
conflict with anything here.

The practical result is that capability is written once and appears in both
agents. The same `plugins/` directory feeds both, the same
`config/mcp.json` registry is read by both, and the same `skills/` directory is
visible to both. Nothing is duplicated per runtime, and the two agents cannot
silently drift apart on a tool name or an MCP server argument, because those
come from one source.

Around that core the project ships a supervisor and two web surfaces:

| Component | Role | Default port |
| --- | --- | --- |
| `packages/portal` | Starts, stops and supervises the child processes; serves the management UI | 3470 |
| `packages/pi-web` | Web UI over pi sessions: chat, model and provider settings, thinking level | 3458 |
| dsh | DeepSeek Harness web UI | 3081 |
| canvas (optional) | A local image-generation service, embedded as a tab | 8188 |

The portal's UI has four tabs: dsh, pi, canvas and manage. The manage tab is
where processes are started and stopped and where per-agent plugin enable state
is edited.

## Requirements

- Node.js `^22.19.0 || >=24.0.0` (from `engines` in `package.json`)
- pnpm (the repository pins `pnpm@11.9.0` via `packageManager`)

The release archive is source-only. It does not include `node_modules` or build
output, so dependencies are resolved at install time for the machine you are on.
A prebuilt tree would not be portable anyway: install selects platform-specific
artifacts, and the optional Tauri shell additionally needs a Rust toolchain,
which cannot be shipped as a substitute for having it installed.

The optional Tauri desktop shell (`desktop/`) additionally needs a Rust
toolchain. Nothing else in the project needs Rust, and the portal is fully
usable in a browser without it.

## Quick start

```bash
# 1. install dependencies
pnpm install

# 2. generate the configuration from the committed templates
pnpm run setup

# 3. start the portal
pnpm start
```

Then open <http://127.0.0.1:3470/>. Start dsh and pi from the manage tab; they
do not launch automatically.

On Windows, `start.cmd` performs all three steps. On macOS and Linux, `start.sh`
does the same:

```bash
./start.sh
```

Both launchers skip the install if `node_modules` already exists, and skip the
setup step if `config/mcp.json` already exists, so they are safe to re-run.

Other scripts in `package.json`:

| Script | What it does |
| --- | --- |
| `pnpm run setup` | Regenerates `config/` from the committed templates |
| `pnpm start` | Starts the portal |
| `pnpm run portal` | Starts the portal directly, without the launcher |
| `pnpm run pi-web` | Starts only the pi web UI |
| `pnpm run build` | Builds `plugin-sdk` and `plugin-host` |
| `pnpm test` | Runs the test suite |
| `pnpm run test:pi-web` | Runs the pi-web test suite |

## Configuration

The `config/` directory mixes committed templates with generated files. The
split exists because some configuration has to name the checkout by absolute
path, and a clone must not carry another machine's paths.

Committed templates and shared state:

| Path | Purpose |
| --- | --- |
| `config/mcp.example.json` | Template for the shared MCP registry |
| `config/hot-plugins.example.json` | Template for the dsh host plugin manifest |
| `config/plugins.json` | Per-agent plugin enable state |
| `config/client-plugins.json` | Client-side plugin switches |
| `dsh/profiles/web/package.json` | The dsh profile: bundles and profile dependencies |
| `dsh/profiles/web/cordis.patch.template.yml` | Template for the dsh mount layer |

Generated by `pnpm run setup`, and gitignored:

| Path | Generated from |
| --- | --- |
| `config/mcp.json` | `config/mcp.example.json` |
| `config/hot-plugins.json` | `config/hot-plugins.example.json` |
| `config/dsh-mcp.patch.yml` | `config/mcp.json`, via `scripts/gen-dsh-mcp-patch.mjs` |
| `config/dsh-home/profiles/web/package.json` | `dsh/profiles/web/package.json` |
| `config/dsh-home/profiles/web/cordis.patch.yml` | `dsh/profiles/web/cordis.patch.template.yml` |

The templates use `{{ROOT}}` where the absolute path of the checkout belongs.
`scripts/bootstrap.mjs` replaces it. Every generated file is rewritten from its
template on each run, so edits made directly to a generated file are not
preserved.

`config/plugins.json` maps agent to plugin name to enabled state:

```json
{
  "ds": { "hello-tool": true },
  "pi": { "hello-tool": true }
}
```

`ds` means dsh and `pi` means pi. A plugin absent from an agent's map is
disabled for that agent.

### MCP registry and environment placeholders

The registry is a JSON array. Each entry is an MCP server, and both runtimes
read the same list:

```json
[
  {
    "serverName": "everything",
    "transport": "stdio",
    "command": "node",
    "args": ["{{ROOT}}/mcp/everything/server.mjs"],
    "description": "Demo MCP server: echo, add, now."
  }
]
```

`transport` is `"stdio"` (with `command`, `args`, and optional `env`) or `"sse"`
(with `url` and optional `headers`). Entries are passed to pi verbatim; each
server's tools are exposed to pi as `mcp__<serverName>__<tool>`, so the demo
server's `echo` tool becomes `mcp__everything__echo`.

Values may reference environment variables:

```json
{
  "serverName": "example",
  "transport": "stdio",
  "command": "${USERPROFILE}/tools/example/run.exe",
  "args": ["--cache", "${XDG_CACHE_HOME:-/tmp/example-cache}"],
  "env": { "EXAMPLE_TOKEN_FILE": "${HOME}/.example/token" }
}
```

- `${VAR}` resolves to the value of `VAR`.
- `${VAR:-fallback}` resolves to `fallback` when `VAR` is unset or empty.
- If a variable is unset and there is no fallback, the placeholder is left
  verbatim. A visibly unresolved `${...}` is easier to diagnose than a child
  process spawned with an empty command.
- Expansion happens when the server is connected, not when the registry is
  read. For `stdio` it applies to `command`, every entry in `args`, and every
  value in `env`; for `sse` it applies to `url` and every value in `headers`.
  The distinction matters because the portal rewrites `config/mcp.json` on
  every enable/disable toggle — resolving earlier would persist this machine's
  paths back into the file.

### dsh MCP rows

dsh consumes MCP servers through its own `@deepseek-ai/dsh-mcp-client` rows, so
`config/dsh-mcp.patch.yml` is generated from `config/mcp.json` rather than
maintained by hand. One row is emitted per server, and both runtimes therefore
agree on server names and arguments. Setting `"dsh": false` on an entry excludes
it from that generated file while leaving it available to pi.

## Writing a plugin

A plugin is a directory under `plugins/` containing a `manifest.json` and an
entry module. The entry exports a factory that receives the neutral API:

```js
// plugins/hello-tool/index.mjs
export default function helloTool(api) {
  api.registerTool({
    name: "hello",
    description: "根据传入的名字返回一句中文问候。",
    parameters: {
      type: "object",
      properties: {
        name: { type: "string", description: "要问候的名字。" },
      },
      required: ["name"],
    },
    async execute(args, ctx) {
      const name = typeof args?.name === "string" ? args.name : "世界";
      return {
        content: [{ type: "text", text: `你好，${name}！` }],
        details: { agent: ctx?.agent },
      };
    },
  });
}
```

The manifest declares what the plugin is and where it can run:

```json
{
  "name": "hello-tool",
  "version": "1.0.0",
  "kind": "tool",
  "targets": ["ds", "pi"],
  "description": "示例工具插件：根据名字返回一句中文问候（共享库最简样例）。",
  "entry": "index.mjs"
}
```

| Field | Meaning |
| --- | --- |
| `name` | Plugin id; the key used in `config/plugins.json` |
| `version` | Free-form version string |
| `kind` | One of `tool`, `command`, `mcp`, `skill`, `ui` |
| `targets` | `["ds"]`, `["pi"]`, or both. Omitted or empty means both |
| `description` | Shown in the management UI |
| `entry` | Entry module relative to the plugin directory. Defaults to `index.mjs`, `index.js`, `index.cjs` or `index.ts` |

Every registration method on the API returns a disposer, and the host tracks
them automatically:

| Method | Registers |
| --- | --- |
| `api.registerTool(def)` | A tool with `name`, `description`, `parameters` (JSON Schema) and an async `execute(args, ctx)` |
| `api.registerCommand(name, def)` | A slash-style command with `description` and `handler(args, ctx)` |
| `api.registerMcpServer(cfg)` | An MCP server, as described in the configuration section |
| `api.registerSkill(skill)` | A skill with `name`, `description` and a Markdown `body` |
| `api.registerUi(def)` | A browser-side extension with `name`, `title`, `slot` and `entry` |
| `api.on(event, handler)` | A listener for `session_start`, `session_end`, `input` or `turn_end` |

Because disposers are tracked, a plugin can be hot-unloaded: unloading runs them
in reverse order. A factory may also return a function, which is called for any
cleanup the disposers do not cover.

Plugins are discovered by `packages/plugin-host`, which scans the shared
directory, filters by `targets` and the enable state, loads each entry through
the adapter for that agent, and isolates failures — one plugin that throws does
not prevent the others from loading.

Skills are the exception to the factory pattern: a `kind: "skill"` plugin ships
a `SKILL.md`, and the shared `skills/` directory is mounted directly by each
runtime. See `skills/hello-skill/SKILL.md` for the shape.

## Architecture

`packages/plugin-sdk` is the contract. It defines the manifest, the six
registration methods and the disposer rule, and nothing else. A plugin imports
only this package.

`packages/plugin-host` is runtime-agnostic. It discovers plugins and drives
their lifecycle, but it never talks to dsh or pi directly — each adapter hands
it a `PluginApiImpl` that knows how to register things natively.

`packages/pi-adapter` and `packages/dsh-adapter` implement that interface once
per runtime.

`packages/pi-mcp` is an MCP client for pi. `packages/portal` and
`packages/pi-web` are the supervisor and the two web surfaces.

See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for how the pieces fit
together, including how the dsh mount layer works and why plugin changes do not
require a dsh restart.

## Troubleshooting

**`[start] configuration is not generated yet`** — run `pnpm install` and then
`pnpm run setup`. `scripts/bootstrap.mjs` checks that the two runtime
dependencies are present before it runs, and exits with a message if they are
not, because the configuration it writes points at paths inside the checkout.

**`pnpm run setup` fails with `missing template`** — a committed template under
`config/` or `dsh/` has been moved or deleted. The script reads templates only
from those two locations.

**dsh reports a missing module on first start** — dsh needs its own profile
under `config/dsh-home`, which `pnpm run setup` creates along with the profile's
`package.json`. dsh does not resolve that profile's dependencies during boot;
they are managed through its `plugin` command, which forwards the remaining
arguments to pnpm inside the profile directory:

```bash
DSH_HOME=./config/dsh-home node node_modules/@deepseek-ai/dsh/lib/bin.js plugin --profile web install
```

The profile depends on `@deepseek-ai/dsh-mcp-client` and
`@deepseek-ai/dsh-skill-filesystem`.

**dsh versions** — `@deepseek-ai/dsh` is an early release candidate, and the
profile bundle graph it resolves (`@deepseek-ai/dsh-base`,
`@deepseek-ai/dsh-web-app`) moves with it. Pin the version you have tested if
you need reproducibility.

**The canvas tab does nothing** — the canvas service is a local
image-generation backend and no install location is assumed. Point
`CANVAS_CMD` at its executable and `CANVAS_CWD` at its working directory. The
default command is `python.exe` on Windows and `python` elsewhere, with
`args` of `main.py --port <port>`.

**`pnpm install` cannot resolve `@aws-sdk/token-providers`** — pi's AWS Bedrock
provider chain asks for a version that is not published on npm. `pnpm-workspace.yaml`
pins the dependency to the newest published version through `overrides`, with the
reason recorded next to it. Remove the override once pi's own chain resolves
without it.

**An MCP server starts with an empty command or path** — check whether its
entry in `config/mcp.json` uses an environment placeholder whose variable is
not set on this machine. An unset variable with no fallback is left verbatim,
so look for a literal `${...}` in the error output.

**Ports are already in use** — the defaults are 3470 (portal), 3458 (pi-web),
3081 (dsh) and 8188 (canvas). Each is overridable: `PORTAL_PORT`, `PI_WEB_PORT`,
`DSH_PORT` and `CANVAS_PORT`.
